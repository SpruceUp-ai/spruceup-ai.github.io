Introduction

Section titled “Introduction”

SpruceUp is a standalone system for making automated, incremental updates to a vector database. It aims to solve a specific problem that is endemic among (though not exclusive to) RAG applications that happen to be attached to a live collection of files; namely, every edit, addition to, or deletion from that collection results in more stale vectors, and as that mismatch increases, the application’s performance degrades.

Admittedly, this problem may appear uninteresting on its face. “How do I keep my datastore up to date?”, is a concern every application with a database has already tackled and solved. But the issue is considerably less trivial when working with vector databases in particular. That’s because the process of getting from a data update event (e.g. this file was edited) to a set of database-ready vector rows is by default both complicated and expensive (e.g. grab the file, parse the data, chunk the text, call a proprietary embedding model…). In fact, the update process is so demanding that many developers don’t even attempt it, preferring to just periodically purge all their vectors and start over.

Enter SpruceUp. SpruceUp watches a file collection for changes, then automatically initiates the multi-step process for making sure those same changes are reflected in the target vector database. What results is a datastore that stays synced to its data source with timely and efficient updates.

Background

Section titled “Background”

Vector search and vector databases

Section titled “Vector search and vector databases”

The conceptual origins of vectors and vector databases are grounded in research into text matching dating back to the 1960s and 70s. Researchers were particularly interested in finding a method for comparing strings of text according to their meaning, and one proposed solution was to encode the semantic content of a given bit of natural language as a sequence of numbers – i.e. as a vector – and then assess semantic closeness by performing mathematical operations on those sequences. Two passages with concordant meaning would show up as highly similar, even if they otherwise differed in word choice, phrasing, or language.

The major technological challenge was, of course, converting text to meaningful vectors. And it took until the 2000’s and 2010’s for major advancements in machine learning to make possible the creation of models that could do that – so-called “embedding models.”

Once efficient embedding models arrived on the scene and started producing large volumes of vectors, there was suddenly a need for a way to store and query all that data. Vector databases began popping up around 2019 to address this need. And while initial use cases were fairly limited, focused mostly on machine learning and recommendation engines, interest exploded when LLMs opened up a promising new possibility: the RAG application.

RAG Applications

Section titled “RAG Applications”

A Retrieval Augmented Generation application is a bit of software that sits between an LLM and a particular set of users and which focuses on improving the LLM’s responses to those users. The prototypical example of a RAG app is a chatbot that specializes in fielding questions from some particular domain – e.g. questions about a company’s HR policies. The role of the RAG application is to pass the LLM whatever supplemental information it might need to accurately answer user questions. (e.g. “This user wants to know about the company’s PTO policy. Below are the relevant sections from the Employee Handbook…”) This technique is primarily useful in cases where users are seeking information that’s absent from the LLM’s training data. Think: proprietary data or data that came into existence after the model’s cut-off date.

The basic, generic architecture of a RAG application

Characteristically, the main task of a RAG application is selective retrieval. Having processed all of the information in a knowledge base or data corpus – i.e. some large collection of files – the app then tries to find all and only the relevant bits to send along with each user’s query.

Getting to that point is a multi-step process. At a minimum, the data corpus needs to be chopped up into smaller chunks; each chunk needs to be processed by an embedding model and turned into a semantic vector; and each vector needs to be stored alongside the original chunk text in a vector database. Once the vector database is populated, incoming user queries are converted into their own embedding vectors which are then compared against the ones in the database to identify the chunks most relevant to the semantic content of the user’s query. Those chunks get returned from the database and conjoined to the user’s query to form the final prompt for the LLM.

Challenges

Section titled “Challenges”

The retrieval step is really the lynchpin of the whole process: Can we consistently pull just the data we need from the database?

There are a few ways this can go wrong. One possibility is that we retrieve only some of the relevant data and thereby deprive the LLM of some of the context it needs to accurately answer queries. Another possibility is that we retrieve excessive and irrelevant data and thereby unnecessarily fill the LLM’s context window, degrading performance and introducing distractors.

There’s another, less obvious way that retrieval can fail: sometimes a RAG app will grab the wrong information because the right information isn’t in the database.

Typically, that happens because the underlying data has changed. That is to say, there was some particular moment in time when we chunked, embedded, and stored our entire data corpus, but since then, we’ve made various changes that are not reflected in the database. And that means our RAG app is feeding stale data to the LLM.

Embedding Rot
Section titled “Embedding Rot”

This problem – sometimes termed “embedding drift” or “embedding rot” – is the core issue that SpruceUp aims to address: how do we keep a RAG application’s vector database fresh when it’s paired with a data corpus that is perpetually changing?

Slowly increasing staleness in a RAG application without incremental updating

One solution would be to periodically trigger a full ingestion: clear out the vector database, rechunk the corpus, recalculate the embeddings, re-store the freshly embedded chunks. A straightforward, hard reset. For RAG apps with small corpuses or slow-to-change data, this may be a perfectly viable option. The RAG team can simply schedule a weekly cron job that runs the full reingestion pipeline.

But it’s an increasingly unreasonable solution as the size of the corpus grows and as the velocity of changes increases. If the hard resets are having to churn through tens of thousands of documents multiple times a week to keep the database acceptably fresh, the team may start to look for a better solution. And for any team working with data that cannot afford to be stale at all – e.g. internal engineering docs, customer-facing product docs, regulatory compliance docs, HR policy docs – the hard reset strategy will be a non-starter. They need something better.

To be clear, there are two areas for improvement here.

First, we can improve on efficiency. The hard reset reingests everything – every single file in the corpus is re-chunked, re-embedded, and re-stored. Unfortunately, some of (often, most of) that effort is wasted on documents that haven’t changed at all. A more efficient solution would selectively re-ingest just those files that have actually changed.

Second, we can improve on how much stale data is in our database and for how long. Most teams can’t afford to do a hard reset after every single edit, and thus, by adopting the hard reset strategy, they are effectively resigning themselves to a certain amount of bad data. They are resigned to letting their database get more and more stale until a full reingestion feels truly justified. A better solution would provide immediate (or near-immediate) reingestion of data right as it is changing.

Solutions

Section titled “Solutions”

The general shape

Section titled “The general shape”

For teams beginning to feel the pain of periodic, hard resets – or for teams starting to roll their own RAG app and looking ahead to the challenges of embedding rot – there is a more sophisticated solution. They could choose to introduce into their application a system for monitoring their data corpus for changes, a system that can calculate exactly which chunks have become stale and promptly update just those chunks in the vector database.

Such a system would improve on the full reset strategy along both of the aforementioned dimensions: no more wasted effort on re-ingesting content that hasn’t changed, and no more stale data sitting for days in the database and continually being served to an LLM.

We might, ideally, want that system to have three other features as well.

First, we might want it to be genuinely automated. Rather than task the engineering team with periodically opening a terminal and running a command to incrementally update their RAG database, the system would watch for changes and initiate updates on its own. (The exact details might vary, of course. It could be a cron job that does incremental updating on a regular schedule or a daemon process that polls for changes or responds to file modification events.)

Second, we might want the system to be compatible with pre-existing RAG applications, being the sort of component that could be added to a mature product right as it starts to really suffer from embedding rot. No need to re-build large components of the app in a different ecosystem. No need to change embedding models or chunking strategies.

Third, we might want the system to have some ability to meet teams, and their data, where they are. Whether that’s a Linux directory full of plain text files or a Google Drive stuffed with markdown, the system would ideally be able to find, monitor, and work with all that data in situ. And if the team has already chosen a particular vector database, the system would ideally be able to integrate directly with that provider – and not require a costly database migration.

Of course, these features won’t be equally important to every RAG team. But they do at least constitute salient comparison points that will help us make sense of the different solutions already on offer.

Existing offerings

Section titled “Existing offerings”

One might loosely organize existing incremental update solutions into three categories. First, there are the “Buy-a-RAG-stack” platforms like AWS, CloudFlare, and Ragie.ai that offer incremental updating inside their ecosystem of managed services and automated RAG products. Second, there are the large, open-source frameworks like LlamaIndex, Langchain, and Pathway that can be integrated with an existing RAG app and which offer incremental updating as a feature. Third, there are frameworks like CocoIndex that specialize in incremental updating for data transformation pipelines.

A multi-dimensional comparison among incremental updating solutions for RAG apps

Buy-a-RAG-stack ecosystems

Section titled “Buy-a-RAG-stack ecosystems”

Amazon Web Services, CloudFlare, and Ragie.ai all offer incremental updating for RAG applications as part of their larger suite of paid services. For AWS users, there’s Amazon Bedrock which can be used to build a RAG app within the AWS stack and which can be configured to do incremental updates. Meanwhile, Ragie.ai and Cloudflare’s AutoRAG both aim to automate the entire RAG application development process, taking care of data parsing, chunking, embedding, storing, and retrieval as part of their managed service. They offer incremental updating as a side benefit of buying in.

While these three services do offer live monitoring and automatic updates, they also sit at the far end of the spectrum in terms of how disruptive they are for an existing RAG stack and for vendor lock-in in general. Developers who want to avoid starting over in a new ecosystem or who simply want a free and open source alternative will need to look elsewhere.

Large frameworks with incremental updating as a feature

Section titled “Large frameworks with incremental updating as a feature”

They could turn to the solutions on offer from LlamaIndex and LangChain.

While LlamaIndex and LangChain are both ecosystems in their own right, they involve far less lock-in. A RAG developer interested specifically in incremental updates could connect to either of these frameworks without needing to start over. For example, the switch to LlamaIndex would at a minimum require a team to adopt the LlamaIndex data model and set up a LlamaIndex compatible bookkeeping datastore. They would also need to periodically invoke the framework’s incremental updating function since, crucially, neither of these frameworks does live monitoring.

Another option – and a more peripheral member of this category – is Pathway. Pathway is also a large framework but specializes in data streaming, rather than LLM integration*.* While Pathway’s incremental updating service is genuinely automated (unlike the aforementioned LlamaIndex and LangChain), integrating Pathway with an existing RAG application is rather more complicated. To adopt Pathway, a team would need, among other things, to rewrite their vector database querying logic to communicate with Pathway’s REST API, to setup, run, and maintain a docker service to manage the monitoring daemon, and to learn enough of Pathway’s streaming programming model (and the associated concepts – e.g. connectors, tables, streaming operators) to be able to engage in moderate amounts of customization.

A framework specialized in incremental updating

Section titled “A framework specialized in incremental updating”

A final option is CocoIndex, an open-source data transformation framework that specializes in incremental updates. Their product is not specifically focused on RAG apps or even vector databases but is, rather, a generic platform for transformations broadly construed (which could encompass, e.g., a pipeline that creates a markdown summary from Github repos and another that creates a neo4j knowledge graph from a podcast feed.)

CocoIndex does have a live monitoring option, can be used without integrating into a larger ecosystem, and does have a wide variety of connectors to popular data sources and databases. It is an immensely flexible dataflow framework with a production-grade Rust core, designed to perform efficient incremental updating on any data pipeline that builds on top of it.

But its flexibility comes with an attendant amount of complexity. While not the largest or most complex framework, CocoIndex does have its own non-trivial learning curve, with its own data model, dependency injection mechanism, SDK, and wide array of optional features. It’s left up to the CocoIndex user both to write the orchestration logic for their data pipeline and to understand the framework well enough to wrap that logic in CocoIndex’s declarative style. And while there are a number of valuable features – including the --live flag for automatic updating – the developer needs to know that these features exist, understand the problem space well enough to know how / whether to use them, and remember to set them.

CocoIndex lies at the other end of the spectrum from AWS and Cloudflare in terms of both vendor lock-in and specialization. It is genuinely ecosystem agnostic and, unlike those big players, is narrowly focused on incremental updating in particular.

This is where SpruceUp lives, too.

Our solution: SpruceUp

Section titled “Our solution: SpruceUp”

SpruceUp is a standalone system that is ecosystem-agnostic and narrowly focused on one task: automatic, incremental updating for RAG pipelines. Compared to the other players in the space, it’s more of an appliance than a framework – less something to learn than something to set up and turn on. Like CocoIndex, it has all three of our previously articulated features: it does live monitoring and automatic updating; it doesn’t require database migrations or substantial rewrites; it does offer multiple connectors to various embedding models, vector database providers, and data sources.

A RAG application using SpruceUp for incremental updating

Being narrowly focused on RAG applications, SpruceUp lacks the flexibility of CocoIndex and has fewer overall services than all of the aforelisted products and ecosystems. Which means, it’s not a perfect fit for every team. The Buy-a-RAG stacks are a better solution for those already ensconced in one of those ecosystems or who prefer a quick, hands-off development process from a proven provider. The LLM integration frameworks will appeal to teams whose LLM-powered apps are already hooked into one of their ecosystems as well as to teams for whom incremental updating is just one among many needed services. CocoIndex will be a better fit for teams juggling multiple AI workloads (e.g. RAG, streaming, structured extraction) and wanting to support all of them with a flexible incremental updating platform.

In contrast, SpruceUp is a good fit for teams who just need incremental updating and want something simple and opinionated.

In terms of simplicity, SpruceUp is by far the most lightweight of the options we’ve looked at. It is, again, more of an appliance than a framework – with all the associated benefits and costs. To integrate with SpruceUp, a RAG developer primarily just needs to create a spruceup_pipeline.py file that (a) contains their app’s existing data transformation logic inside a single transform function and (b) makes a call to a custom define_config function specifying the user’s preferred data source(s), embedding model, and target database. There is no framework-specific data model to be learned, no complex dependency injection mechanism to be grappled with, no custom SDK.

As for being opinionated, consider a feature that is present in both SpruceUp and its nearest neighbor, CocoIndex: caching and embedding batching.

The engineers behind both projects are aware that there are significant performance improvements to be had by caching the results of expensive transformation functions – e.g. external embedding model calls. Accordingly, both projects provide the user with a toolset for using that feature in their pipeline. The difference is at the embedding step, in particular. CocoIndex exposes a memo flag that must be explicitly assigned to True for a sub-function’s results to be cached. Which means, again, it’s up to the user to be aware of the feature and of its importance. SpruceUp in contrast memoizes embeddings by default. We think that those savings are too important to leave on the table.

Similar remarks apply to batching calls to embedding models. Given the speed at which smaller files can be processed, there is a real concern that pipelines making an embedding request per-file (or, worse, per-chunk) will hit rate limits and start receiving 429 Too Many Request errors. The obvious intervention is to batch our embeddings, turning single-file requests into multi-file requests. Again, both teams are aware of this.

While CocoIndex’s simple, out-of-the-box embedding operations do batch by default, the typical user’s custom CocoIndex pipeline – which makes an API call in-line and once per chunk or file – won’t. To take advantage of this core efficiency, the user needs to know this feature exists in the framework, understand its purpose and potential, and remember to turn it on for their custom pipeline.

SpruceUp, on the other hand, batches embeddings by default. SpruceUp is opinionated, and our opinion is that defaults matter.

Architecture

Section titled “Architecture”

Overview

Section titled “Overview”

SpruceUp is effectively a wrapper on a RAG application’s data transformation pipeline, adding the incremental update functionality but otherwise leaving the process unchanged. Unsurprisingly, then, user data moves through SpruceUp in essentially the same way it would move through a RAG app. Upon being edited, a user’s file is retrieved, then chunked and embedded, then the resulting vectors are compared against what was generated on the previous run, with all differences written to the user’s vector database.

Here’s a more detailed description of the same process, with an emphasis on the components that facilitate the incremental updating.

Let’s start with the user. To actually use SpruceUp, the would-be user needs to install the spruceup-ai Python package in their project, needs to create a spruceup_pipeline.py file in that project directory, needs to add their data pipeline’s transformation logic to that file and calls define_config to set their preferred data source, embedding model, and target vector database, and, lastly, needs to run spruceup start from a terminal. That starts SpruceUp, and it will continue to run, monitoring the user’s data corpus and incrementally updating their vector database, unless and until it is terminated.

The first important thing that happens upon startup is the creation of a Monitor object whose job is to detect changes in the user’s data corpus. It will persist as a daemon process for as long as SpruceUp remains running, catching incoming file changes either by waiting for OS-level event notifications (for local files) or through polling (for cloud-hosted files.) The Monitor starts off in a catch-up phase. During this phase, the Monitor does file-level diffing to identify all the changes that have occurred among the user’s files since the last time SpruceUp ran. Each changed file is incrementally updated. Once those catch-ups are done, the Monitor enters a watching phase where it waits for new edits to occur.

During both phases, each incoming change gets represented as a sync task, and each sync task is added to a queue. The queue is drained by a Coordinator object whose job is to guide files through the incremental update process. For each sync task, the Coordinator first retrieves the file’s contents then calls the user-defined transform function to turn that content into vectors. Those vectors are then passed off to the SyncEngine which compares them against our manifest database – a local record of what exists in the user’s vector database – to make a determination about what needs to be incrementally updated.

A high-level overview of SpruceUp’s incremental update architecture

That’s the core functionality. Every other complexity in the application is there either to make things more efficient (processing sync tasks concurrently, batching embedding calls, memoizing sub-function results and embeddings), to give the user more options (adding connectors to different embedding models, vector databases, and data sources), or to improve correctness (ordering database transactions, generating idempotent writes, retrying failed updates.)

In the remainder of this section, we will explore some of SpruceUp’s more interesting components and decisions, starting with the engineering challenge at the core of the app: keeping the user’s data source simultaneously synced to two different databases. We’ll then look at a couple of the more complex add-on features: sub-function memoization and embedding batching.

Eventual Consistency

Section titled “Eventual Consistency”

The manifest

Section titled “The manifest”

Very early on in development we decided that SpruceUp would integrate with each user’s existing vector database – and not require them to migrate. This decision had a cascading impact on the rest of the application.

First, there was the matter of bookkeeping. Accurate incremental updating requires up-to-date records about the state of the user’s corpus and datastore, and those records need to encompass more than what’s typically present in the user’s vector database. For SpruceUp to work, we need to track various facts at the chunk-level and at the file-level and at the data-source level.

That’s a lot of bookkeeping data. And we had essentially two options for storing it all: we could create new tables within the user’s vector database, or we could maintain a separate, local database. The former option would allow us to have truly atomic update transactions within a single database, but we’d have to implement the bookkeeping logic separately for every vector database connector. Worse: for any pipeline with a cloud-based database (e.g. from Pinecone), we’d be increasing the number of cross-network writes by an order of magnitude. In contrast, the local option would save a significant amount of time on reads and writes but would require us to carefully design an updating strategy that could guarantee eventual consistency across two databases.

We decided to go with the local option since the latency costs of doing our bookkeeping over a network connection seemed prohibitive. More specifically, we adopted SQLite – a battle-tested and lightweight relational database. With SQLite, all of our bookkeeping needs could be met by a single .db file that lives in the user’s project directory. Plus, the usual drawbacks were largely a non-issue for our app: our bookkeeping needs could be met without complex user account controls, without cross-network SQLite access, and without concurrent writes. (SpruceUp is a single-user application with a Python core, and Python’s Global Interpreter Lock was going to serialize our bookkeeping writes anyway. So it’s no problem that serial writes are all that SQLite supports.)

The SQLite .db file is our manifest: a complete record of the user’s data sources, files, and chunks with separate tables for caching memoized results and for saving various hash values that get used for diffing.

But we did still face the complication of non-atomic transactions. With two separate databases to keep synced – both with each other and with the user’s data – we needed a plan for how we’d recover from failures. We needed a way to guarantee eventual consistency regardless of when in the long series of writes that accompany each incremental update a failure might occur.

Before looking at our solution, let’s briefly consider one other design decision that contributed to the complexity of keeping everything synchronized: our use of multi-level diffing.

Multi-level diffing

Section titled “Multi-level diffing”

The naive approach to syncing a changed file is, essentially, to do a full reset in miniature: clear out all of the old records associated with that file, then re-chunk, re-embed, and insert the newly generated vectors. But that’s unappealing for essentially the same reason that fully resetting an entire data corpus is unappealing. Namely, it’s inefficient. Imagine, for instance, that the user has just made a small edit to the conclusion paragraph of a large text file that generates a thousand different chunks. We could delete, re-embed, then re-insert all 1,000 of them… but ~999 of them don’t need it. Most of that work would be wasted.

SpruceUp’s file- and chunk-level diffing

This is why SpruceUp has multiple levels of hash-based diffing. An initial round of diffing is done by the Monitor component. It picks up file-level changes by looking first at the modified time for each file and then, for each modified file, diffing the file’s current contents against our records in the manifest. Later on, the SyncEngine does another round of diffing, this time comparing each chunk’s contents against our records in the manifest.

Both file- and chunk-level diffing are used to make decisions about what to update. The file-level comparison is how we decide which files need to be incrementally updated. The chunk-level comparison is how we decide which chunks need to be upserted (or, in the case of orphaned chunks, deleted.)

The challenge

Section titled “The challenge”

As a consequence of these two decisions – local bookkeeping and multi-level diffing – each sync task requires three separate writes. There’s (a) the write to the user’s vector database to record the file’s new vectors, (b) the write to the manifest’s chunks table to record the file’s current chunks, and (c) the write to the manifest’s files table to record the file’s new contents.

The way that SpruceUp ensures (eventual) correctness in the face of failure is twofold. First, we ensure that these three writes happen in a particular order and are always done idempotently. Second, we use a simple state machine to track each file’s journey through the SpruceUp pipeline so that we can identify and retry failed updates.

Ordered, idempotent writes
Section titled “Ordered, idempotent writes”

The goal when ordering the three writes was to always err on the side of the user’s vector database being more correct than it appears. What we specifically needed to worry about was when, precisely, it was safe to update the data that we’re using to make decisions (i.e. the diffing data.)

As we’ve seen, the Monitor makes decisions about which files need to be updated using data in the files table; the SyncEngine makes decisions about which chunks need to be updated using data in the chunks table; and the vector database isn’t used for decision-making.

The order of writes when updating a changed file with SpruceUp

That last fact is key. It explains why the vector database must be written first. Since no decisions hinge on the actual state of the user’s vector database, updating it first means it is never less correct than the manifest and will never be the cause of persistent inconsistencies. Should the app crash during or after the vector database write, both the Monitor and the SyncEngine will continue believing the file and its chunks are stale. Thus, on the next run, the file will get re-processed and, at worst, we will idempotently tell the vector database to update some rows that have already been updated or to delete some rows that have already been deleted.

The vector database write is safe, and it always happens first. Only when that’s done do we update the chunks table. And then only once the chunks table is updated do we update the files table. This third and final write is what marks the incremental update process as complete. From here on – or until the next edit – this particular file will appear synced whenever Monitor diffs it.

The entire process of syncing an edit

The SyncSweeper
Section titled “The SyncSweeper”

The ordering of writes is how we ensure both that the vector database is never less correct than the manifest and that, post-crash, any files associated with a failed sync task will continue to look stale to the Monitor.

But what about files that fail and not because of the application crashing? (Which, ideally, would be the more common occurrence!)

Such failures are handled by a separate component, the SyncSweeper. The SyncSweeper does its job with a simple state machine that tracks the status of each file.

The state machine works like this. One of the first things the Coordinator does upon receiving a sync task is to write to the files table, marking the current file’s sync_state as "in-flight". The file is then processed in the usual way. Only after the SyncEngine writes to the user’s vector database and to the chunks table does the file’s sync_state get updated to "synced". If the sync task should fail at any point, the Coordinator will instead update its status to "failed". (There’s also a fourth state value, "needs_reindex", that is used to disable chunk-level diffing for a file that needs all of its chunks to be fully re-upserted – as when, e.g., the user’s embedding model configuration has changed.)

The SyncSweeper’s state machine

It’s the SyncSweeper’s job to handle those "failed" files. It’s set to wake up once a minute as well as every time the task queue drains. The SyncSweeper scans the state machine for failures then pushes any it finds back into the task queue to be retried. This mechanism ensures that transient, non-terminal failures are quickly addressed and don’t cause the databases to drift apart from the actual data corpus.

After a terminal failure, of course, any files that were in the midst of being processed when SpruceUp crashed will still be marked as "in-flight". To address this, SpruceUp’s main application logic includes a startup sweep that changes all "in-flight" files to "failed".

The catch-up phase buffer
Section titled “The catch-up phase buffer”

There is one final consistency detail worth mentioning.

As previously discussed, SpruceUp’s execution has two phases: a catch-up phase where edits made since the last run are applied and a live monitoring phase. But this design creates two interconnected issues. First, how do we ensure that we are properly detecting edits while the catch-up phase is running? And, second, supposing we are detecting those edits, how do we prevent a race condition? (e.g. imagine two incoming edits to README.md: one done while SpruceUp was down and another done during catch up. How do we ensure that those two sync tasks complete in the order in which the edits occurred?)

Our solution is to launch the Monitor and set it to tracking edits immediately on startup. During catch-up, it writes incoming sync tasks to a secondary buffer queue. Only after the phase transition does the buffer get flushed into the main task queue.

Efficiency features

Section titled “Efficiency features”

Besides freshness, the other major motivation for creating an incremental updating system is efficiency. And that remained an important consideration when deciding how to build SpruceUp; indeed, a number of its more complex sub-systems were added solely in the name of efficiency. We address two of those systems below: caching and embedding batching.

Caching

Section titled “Caching”

Unsurprisingly, the locations we identified as the most likely targets for efficiency gains were the steps with the highest latency (and monetary) costs: file retrieval, embedding generation, and user-defined cross-network transformations.

Embedding generation and file retrieval are non-negotiable RAG steps. Every pipeline needs them, and both are potentially expensive. Every embedding step and many file retrieval steps – the ones for cloud-hosted files – will incur the full latency cost of a roundtrip network request, in addition to the actual monetary cost associated with calling an embedding model. Beyond those non-negotiables, a user can also introduce any number of other custom transformation steps with their own significant costs. (Imagine, for instance, a pipeline that asks an LLM to generate a short summary for each file.)

A bare-bones incremental updating system would leave those per-file costs in place. Each edited file would need to be re-downloaded, re-embedded, and re-transformed. Every time, every edit. Yet much of that work would often end up being unnecessary.

SpruceUp is designed to avoid redundant per-file work by means of caching, which happens in three separate layers. There’s a @memoize decorator layer that lets the user decide what to cache. There’s a layer that automatically saves embeddings. And there’s an optional layer that can store each file’s contents in the manifest.

The @memoize decorator
Section titled “The @memoize decorator”

The first caching layer is user-facing and optional.

Example of a memoized sub-function

Each user’s custom transformation function can include any number of data manipulation steps, including high-latency network requests, computationally expensive conversions, or pricey LLM calls. We can’t anticipate each user’s needs nor pre-determine which parts of their pipeline are expensive and slow. Instead, we turn that decision over to the user, exposing an optional @memoize decorator that they can deploy as-needed to turn on caching. To use it, a user needs to extract each expensive step into a separate helper function and then wrap that function in the decorator. SpruceUp will then take charge of caching the function’s results, saving them in SQLite, and serving them back on subsequent runs, as appropriate. (It’s appropriate to return the cached results for a memoized sub-function when and only when the same file is being re-processed and the same sub-function is being re-invoked with the same arguments.)

Embedding caching
Section titled “Embedding caching”

SpruceUp also caches embeddings.

In our testing, the embedding step could sometimes occupy as much as 85% of the wall-clock time when doing an initial ingestion on a simple user pipeline. (While that percentage declines if the user’s files are mostly cloud-hosted, if the user’s vector database is non-local, or if there are other expensive steps present in the user’s transformation function, it remains significant – often in the 40-50% range.)

Accordingly, this is likely the most important caching efficiency in a typical RAG app, and we don’t expose it as a user-facing toggle. Rather, SpruceUp simply checks the embedding cache every time the embedder gets called during a transform. If there’s a hit – i.e. if the chunk belongs to a file with the same file_id, and has exactly the same content hash as before – we return the previous embedding and skip the expensive network call.

Caching for the both user sub-function transforms and embeddings

One complication that arises for embeddings in particular is that seemingly minor changes in the user’s pipeline can spoil both the cache and vector database. If a user changes their embedding model or even alters the exact number of dimensions per vector, all of their existing embeddings are invalidated. That’s because vectors from different models as well as vectors of different sizes are fundamentally incompatible with one another. They should not be co-present in a vector database.

To address this possibility, SpruceUp does a check on each startup to see whether the user has changed models or dimensions. Either change will trip the force_reindex flag, which causes both the cache and the vector database to be cleaned out, followed by a re-run of the entire pipeline from scratch.

File content caching
Section titled “File content caching”

Those are not the only two events that can trigger a full reset. The force_reindex flag can also be thrown should the user change their vector database configuration (including the provider or table schema) or edit their transform function (including any memoized sub-functions.) Any of these changes must be treated as invalidating the user’s existing vector database and should cause a full reset.

Full resets are, however, the most expensive operation SpruceUp can perform. This is where our third layer of caching comes in.

To avoid the need to retrieve everything from disk during a force reindex, a user can also cache the raw bytes for each file. This cache has no effect on incremental updates – since, by definition, an incremental task is working on an altered file – but it does help with full resets. For a large corpus on a cloud-mounted volume, having a local cache of each file’s contents can double the speed of a full reindex.

That said, the obvious downside is that file caching duplicates the user’s data corpus inside of the manifest. A large corpus means a large manifest, and a large manifest can start to press against the upper bounds of SQLite’s high-performance region. At some point, the efficiency gains from faster reindexing may not offset the efficiency losses (to say nothing of other reasons for wanting to preserve disk space.) Moreover, users with primarily local files as well as those who tend to leave their transform alone (thus, never triggering a full reindex) will receive no benefit at all. For this reason, file caching is off by default but can easily be turned with the optional cache_files=True argument in a user’s define_config function.

Concurrent co-routines and embedding batching

Section titled “Concurrent co-routines and embedding batching”

Beyond caching, the most significant efficiency features in SpruceUp are embedding batching and concurrent processing of sync tasks. Both were implemented to reduce the latency generated by the embedding step – which is the largest source of lag in the typical user pipeline.

Rather than let SpruceUp sit idle while waiting for responses to come in from the model provider, we organize our sync tasks as concurrent co-routines, using Python’s asyncio library, which allows the app to efficiently task-switch. With asyncio, the Coordinator can have multiple sync tasks in-progress at the same time and can seamlessly move the main execution thread between them as individual routines hit a stopping point (like, for instance, await-ing a response from an embedding model.) Even without true multiprocessing, SpruceUp’s async concurrency is a huge efficiency bump – our load testing suggests the application runs roughly ten times faster with concurrency turned on.

The other efficiency feature that was added to address the high latency of embedding calls is embedding batching.

The typical RAG pipeline is going to make a call to an embedding model either once per chunk or once per file – either of which is much too frequent to avoid rate limiting from embedding model providers. Thus, instead of letting the user call an embedding model directly, we expose an embed method that appears to call the model once per file but actually routes the request to an EmbeddingBatcher object. That object first checks the embedding cache, and upon a cache miss, it pools together all of the incoming chunks – often from multiple files – before sending them off in large batches to the embedding model.

Cross-file embedding batching

The entire process works like this. The user’s transform function receives as input both the raw data from a given file and the aforementioned embed method. Once they’ve turned their file into a list of chunks, they pass those chunks into an embed call and await the embeddings. Under the hood, the embed call is actually an alias for a process_chunks method defined on the EmbeddingBatcher. It first checks the embedding cache for each of the passed-in chunks, and on a cache miss does three additional things.

First, it creates an in-memory future – i.e. a promise to attempt to complete some work at a later point in time – for each pending chunk. In this case, the promise is that the EmbeddingBatcher will retrieve an embedding for that chunk. Second, the EmbeddingBatcher adds the current file’s chunks to a common pool, which is, essentially, a waiting room for chunks that still need embeddings. Third, the EmbeddingBatcher wakes up an event-driven flusher process to check on the pool of waiting chunks. If the pool has grown large enough or if enough time (1000 ms) has passed, the flusher splits the pool into large batches and sends each batch off to the embedding model. (The pool is “large enough” when it contains at least as many chunks as the max_batch_size allowed by the user’s embedding model provider.) The flusher then goes back to sleep and execution passes to some other co-routine.

When the embeddings finally come back from the provider, the EmbeddingBatcher distributes them back out to the individual chunks, thereby resolving each chunk’s future. A list of embeddings are passed back to the user when (and only when) every future for every chunk in a particular file has been resolved. At that point the sync task for that file unfreezes and can continue processing the user’s transform function, embeddings in hand. If, on the other hand, any steps taken inside of the EmbeddingBatcher fail, all affected files have their sync_state set to "failed" and all affected chunks’ have their futures marked as done and set with an exception.

Future Development Plans

Section titled “Future Development Plans”

Our future plans to build-out SpruceUp encompass fixing a few tough edge cases and adding a handful of valuable features.

Known edge cases

Section titled “Known edge cases”

One existing edge case that we’d like to tackle more gracefully is failure handling for updates on corrupted files. Currently, every attempt to update a corrupted file results in the associated sync task being marked as failed, logged to the console, and then picked up by the SyncSweeper to be re-added to the task queue. (At which point it fails again, logs again, and so on.) We’d like to implement some dead letter state tracking for corrupted files to prevent this sort of infinite retry loop.

A second known edge case involves a specific race condition that can occur for certain pipeline set-ups with more than one data source of a particular type. Suppose a user has pointed SpruceUp at two separate Google Drive directories and both are synced to their database. Then the user moves a file from one directory to the other, generating two separate sync tasks: a deletion from source A and an upsert to source B. Currently, the two tasks may end up racing. Depending on a series of timings, things could either turn out fine, data could go missing, or data could be duplicated. Fixing this will require adjustments both to our manifest schema and to the debounce logic in our task queue.

Additional Features

Section titled “Additional Features”

The top priority for feature development is adding more connectors – to more embedding model providers, to more vector databases, to more data sources.

We currently have connectors to four different embedding providers (OpenAI, Voyage, Cohere, Gemini); however, all of these providers are remote and proprietary, meaning we have no way to support a RAG application that generates its embeddings from a self-hosted, open-source model. That’s the next priority for this connector type.

We currently have connectors for three different vector databases (pgvector, Pinecone, and Weaviate), but there are a number of other large players in the space like Qdrant and Milvus that we’d like to support.

Most critically, we currently have connectors for only two different data sources (local drives and Google Drive). And while source connectors are the hardest to build, they also add the most value to our connector library. At a minimum, we’d like to add connectors for Notion, Github, Dropbox, and OneDrive.

Another direction for future development is adding support for RAG applications that use hybrid-search across both sparse and dense vectors. (In this context, “dense vector” is just a more specific name for the same data structure we’ve been talking about this whole time: a list of numbers that represents the semantic content of a bit of natural language. A sparse vector, in contrast, is a list of numbers that represents the lexical content of a bit of language, capturing the particular words present and their individual frequencies.) While the current version of SpruceUp was designed with only dense vectors in mind, hybrid search is becoming more popular and is increasingly regarded as a best practice for RAG apps.

Finally, we’d like to add some out-of-the-box transformation functions that a SpruceUp user could drag and drop into their transform, as an accessibility feature. (Think, e.g., functions that implement basic parsing and chunking strategies.) That’s a lower-priority addition, but it would help us lean into SpruceUp’s positioning as the lightweight option in the incremental update space.
